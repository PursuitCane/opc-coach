# 技术架构骨架

> 工程视角文档，给技术评审 / 开发对齐用。不讲卖点，讲组件、数据模型、pipeline、边界、选型。
> 叙事版见 `tech-highlights.md`；本文件是它背后的工程实现骨架。
> 主干：① 商业状态图谱（状态） + ② 决策闭环反馈回路（反馈）。

## 0. 一句话架构

用户对话 → 抽取成结构化的「商业状态图谱」→ 优先级引擎决定追问什么 → 检测到决策后追踪回填结果 → 结果作为反馈信号校准 coach 策略。图谱是"状态"，反馈回路是"进化燃料"。

## 1. 组件分层（文字版组件图）

```
┌─────────────────────────────────────────────┐
│  交互层  对话 UI / 图谱可视化 / 回填提醒        │
├─────────────────────────────────────────────┤
│  编排层 (Harness)                            │
│   - 对话编排 / Skill 路由 / 会话状态机         │
├──────────────┬──────────────┬───────────────┤
│  抽取管线      │ 优先级引擎    │ 决策闭环引擎    │
│ (对话→图谱)   │ (该做什么)    │ (检测/回填/eval)│
├──────────────┴──────────────┴───────────────┤
│  Skill 层  PMF / 融资 / 定价 / 增长 …          │
│           (prompt + 工具 + 知识库 + eval)      │
├─────────────────────────────────────────────┤
│  grounding 层  搜索 / 行业数据 RAG / benchmark │
├─────────────────────────────────────────────┤
│  存储层  图数据库 + 向量库 + 事件日志 + 数据集   │
└─────────────────────────────────────────────┘
```

依赖方向：上层调下层。编排层是唯一入口，其余模块互不直接调用，全部经编排层协调。

## 2. 数据模型：商业状态图谱

图谱是核心状态。节点四类，边表达因果与时序。

**节点：Hypothesis（假设）** —— 图谱一等公民
```
id, founder_id
statement        # "早期用户愿为 X 付 Y 元"
type             # 用户/需求/定价/渠道/竞争/团队 …
status           # proposed | testing | validated | refuted | stale
confidence       # 0-1，随证据更新
impact           # 影响度 0-1（错了后果多大）
uncertainty      # 不确定性 0-1（多没谱）
test_cost        # 验证成本 0-1（多难验）
priority_score   # = impact × uncertainty × (1 - test_cost)，引擎算出
evidence_refs[]  # 关联的 grounding 证据 / 结果
created_at, updated_at, version
```

**节点：Decision（决策）**
```
id, founder_id, statement
linked_hypotheses[]   # 基于哪些假设做的
expected_outcome      # 当初预期
status                # open | executed | resulted
made_at
```

**节点：Action（行动）** `id, decision_id, description, done_at`

**节点：Result（结果）** —— 反馈回路的产物
```
id, decision_id
outcome            # 实际发生了什么（回填而来）
metric_delta       # 关键指标变化
verdict            # success | partial | fail
backfilled_at
```

**边（关系）**
```
Hypothesis --supports--> Decision
Decision   --triggers--> Action
Action     --produces--> Result
Result     --updates-->  Hypothesis   # 结果反过来改假设 status/confidence
Hypothesis --revises-->  Hypothesis   # 信念修正：新版本覆盖旧版本
```

**信念修正**：口径变更不删旧节点，建新版本 + `revises` 边指向旧版本，旧版本置 `stale`。图谱始终自洽且保留演进痕迹（这也是数据资产）。

## 3. 端到端 Pipeline（一句话怎么流到进化）

**A. 摄入与抽取（对话 → 图谱）**
1. 用户发言 / 上传材料进入编排层。
2. 抽取管线调 LLM，做结构化抽取：识别其中的假设 / 决策 / 行动 / 指标，输出 JSON（受 schema 约束）。
3. 归并去重：新抽取项与图谱现有节点比对（向量相似 + LLM 裁决），命中则更新/建 `revises` 版本，否则新建节点。
4. 写入图数据库，节点文本同时写向量库。

**B. 判断该做什么（图谱 → 追问）**
5. 优先级引擎（确定性代码）对所有 `status ∈ {proposed, testing}` 的假设算 `priority_score` 排序。
6. 取 top-N 高危假设，交编排层。编排层决定：直接 challenge / 分派某个 Skill / 触发 grounding 取证据。
7. 生成回复（LLM，带 grounding 引用），推进对话。

**C. 决策闭环（追问 → 反馈 → 进化）**
8. 决策检测（LLM）：识别本轮是否产生 Decision 节点，记录 `expected_outcome`，置 `open`。
9. 调度器（代码）按预期验证周期，到期通过回填提醒触发用户回填 Result。
10. 回填到达 → 写 Result 节点 → `updates` 边回改关联假设的 status/confidence。
11. Eval：把 `(上下文 → 决策 → 预期 → 真实结果)` 落成一条评估样本；离线用它评估"当初的追问/判断质量"，产出策略调整信号。
12. 策略迭代：用 eval 信号优化抽取/提问/排序的 prompt 与参数。这是"自进化"的落点，离线批处理，不在实时链路。

## 4. LLM vs 确定性代码（可靠性 & 成本边界）

| 环节 | LLM | 代码 | 说明 |
|------|-----|------|------|
| 结构化抽取 | ✅ | | schema 约束输出，可靠性靠 schema + 校验 |
| 节点归并裁决 | ✅ 辅助 | ✅ 主 | 先向量粗筛（代码），边界情况 LLM 裁决 |
| priority_score 排序 | | ✅ | 纯公式，可解释、零幻觉、免费 |
| 决策检测 | ✅ | | 分类任务 |
| 回填调度 | | ✅ | 定时器/队列 |
| 归因打分/Eval | ✅ 辅助 | ✅ | 结果比对为主，质量判断用 LLM |
| 策略迭代 | 离线 | ✅ | 不在实时请求链路 |

原则：**能用公式的绝不用 LLM**（排序、调度、指标比对），把 LLM 收敛在"理解自然语言"这件它真正擅长的事上——降本、降幻觉、可解释。

## 5. 存储选型

- **图数据库**（Neo4j / 轻量可先用 Postgres + 邻接表）：节点与关系，图谱状态的权威来源。
- **向量库**（pgvector / 专用）：节点文本 embedding，做归并粗筛与结构化检索的语义召回。
- **事件日志**（append-only）：所有原始对话与状态变更，可回放、可审计，是重建图谱的底账。
- **评估数据集**（结构化表）：`(上下文 → 决策 → 结果)` 样本，喂给离线 eval 与策略迭代——**这是护城河数据资产的落盘处**。

检索策略：图查询（结构/时序）+ 向量召回（语义）两路合并，而非全量回灌聊天记录。

## 6. MVP 收敛（demo 该做到哪）

- 可假数据演示：决策检测 + 一次回填 + 图谱状态翻转（C 段前半）。
